FEATURE: Conversational Assistant Logging (no manual tracking)
--------------------------------------------------------------------------
Problem:
  Most habit/journal apps fail because manually opening the app and filling
  forms for every habit/check-in is friction. A busy user often just stops
  logging after a few days.

Idea:
  The user opens the app and simply talks/types to an assistant (chatbot)
  about their day in plain language - e.g. "woke up at 7, went to the gym,
  skipped meditation, slept like 5 hours, felt pretty stressed about work."
  The assistant parses this and automatically creates/updates the relevant
  records (habit logs, check-in entries, maybe even draft decision-journal
  entries) - the user never fills a manual form.

Why it matters:
  This turns Life OS from "another tracker you have to maintain" into
  something closer to just narrating your day to a friend - removing the
  single biggest reason these apps get abandoned.

Rough technical approach:
  - A chat endpoint (e.g. POST /assistant/message) that takes the user's
    free-text message
  - An LLM call that extracts structured intents from the message: which
    habits were done/not done, check-in values (mood/energy/sleep/stress),
    and any other loggable events
  - A mapping/confirmation step: show the user what was understood
    ("Marked: Gym - done, Meditation - missed, Sleep - 5h, Stress - high.
    Correct?") before committing to the database, so misunderstandings don't
    silently corrupt data
  - Once confirmed, the assistant calls the same underlying services/
    endpoints that manual logging already uses (Habit/HabitLog/CheckIn
    services from Phase 1) - it's a new input method, not a new data model
  - Conversation history could itself become useful data later (tone,
    recurring themes) but that's a separate, later idea

Dependencies / prerequisites:
  - Requires Phase 1 (habits, check-ins, streaks) to already exist, since
    this feature is just a smarter way to fill the same data
  - Requires an LLM integration (API call), which is a new type of external
    dependency for this project - needs its own cost/rate-limit thinking
  - Needs a review/confirmation UI step on the frontend so users can correct
    misunderstood entries before they're saved

Where this fits:
  Best considered after core Phase 0-3 functionality is working, as an
  alternative "smart" input method layered on top of the existing data
  model - not a replacement for the manual UI, but an additional way in.

FEATURE: Decision Journal + Life Areas / Goals (suggested "Phase 5")
--------------------------------------------------------------------------
Problem:
  The vision is "decision intelligence across every area of life", but today
  Life OS only tracks habits and daily state. Decisions - the other half of
  the vision - aren't captured anywhere.

Idea:
  - Life areas: user-defined groups like Health, Career, Finance,
    Relationships. Habits (and later decisions/goals) can belong to one.
  - Decision journal: record a decision when it's made (context, what was
    decided, expected outcome, a follow-up date), then come back later and
    record what actually happened and rate it 1-5.
  - Goals (optional, later): a target per life area that habits contribute to.

Why it matters:
  Reviewing past decisions against their real outcomes is how people get
  better at deciding. It also gives the intelligence layer a new kind of
  data: e.g. "decisions made on low-sleep days turn out worse".

Rough technical approach:
  - Tables are already designed in database_design.txt ("PHASE 1 (deferred
    pillar)"): life_areas, decisions, plus habits.life_area_id (SET NULL).
  - Endpoints: CRUD /life-areas, CRUD /decisions, PATCH /decisions/:id for
    the follow-up (actual_outcome, outcome_rating).
  - Follow-up reminders: reuse the Phase 4 reminder job + notifications
    table ("Time to review: <decision>" on follow_up_date).
  - Insights: correlate outcome_rating with check-in metrics on decided_at,
    reusing correlation.service.
  - Add decisions to the /export endpoint.

Dependencies / prerequisites:
  - None blocking: Phases 0-4 are done. Frontend should catch up to Phase 4
    first so both sides stay in lockstep.

FEATURE: Python ML Prediction Service (optional item from Phase 3)
--------------------------------------------------------------------------
Problem:
  Streak risk is forecast by a hand-tuned formula ("heuristic_v1"). It beats
  a naive baseline, but its weights are guesses, not learned from data.

Idea:
  A separate Python microservice (FastAPI + scikit-learn, e.g. logistic
  regression or gradient boosting) exposing POST /predict. Express sends it
  the same features the heuristic uses and gets a probability back.

Rough technical approach:
  - The seam already exists: streakRisk.service.js keeps extractFeatures()
    separate from scoreFeatures(), and every forecast carries modelVersion.
  - Train offline from habit_logs/check_ins (the backtest in
    predictionBacktest.js already produces honest point-in-time
    examples), compare against heuristic_v1 with GET /predictions/accuracy,
    and only switch if the Brier skill score is clearly better.
  - Fall back to the heuristic if the service is down or slow (timeout).
  - At that point, revisit the predictions table in database_design.txt to
    log served predictions for monitoring.

Dependencies / prerequisites:
  - Months of real usage data from real users; with one demo account a
    learned model would just overfit. Not worth building before then.

PRODUCTION READINESS (before real users)
--------------------------------------------------------------------------
Not features, but needed before anyone other than the developer uses it:

  - Deployment: Dockerfile for the API, run `prisma migrate deploy` on
    release, a hosting target, and a CI step that deploys after tests pass.
  - Account management: change password, forgot/reset password (needs real
    email), change email, delete account (GDPR-style; cascades already
    exist in the schema).
  - Real email provider: replace the "log" placeholder in
    src/services/mailer.js (nodemailer SMTP, SES, Resend, ...).
  - Multi-instance support: Redis-backed rate-limit store, and move the
    in-process scheduler to a queue (e.g. BullMQ) for retries and
    exactly-once jobs.
  - Prisma 7 upgrade: clears the remaining `npm audit` advisory
    (deepmerge-ts in the Prisma CLI); a breaking major, needs its own pass.
  - Observability: error tracking (e.g. Sentry), request metrics, alerts on
    failed jobs; database backups and a tested restore.
